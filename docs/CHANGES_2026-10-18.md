## 一、Snipaste 冲突（用户报告：运行 fastDictionary 时 Snipaste 截不了图）

**根因**：全局低级鼠标钩子把任何 >10px 的拖拽都当成"划词"。在 Snipaste 里框选截图区域正好是一次拖拽，
于是 fastDictionary 去取词 → 清空剪贴板 + 模拟 Ctrl+C → 打断 Snipaste 的截图会话。

**修复**：
- `selection_guard.go`（新增）：进程黑名单，默认含 snipaste / sharex / snippingtool / screenclip / pixpin / greenshot
- `hook.go`：把目标进程名传进手势回调，钩子里不再做任何慢操作
- 托盘新增「暂停划词 30 分钟 / 恢复划词」
- 设置页「划词」增加黑名单可视化编辑器

## 二、浮动条自己跳出来（用户补充报告）

**根因 1**：资源管理器里双击文件 → 双击触发"选中一个词" → UIA 读不到 → 回退模拟 Ctrl+C → 复制了文件
→ 剪贴板读出文件路径 → 浮动条显示一个路径。

**根因 2**（本会话引入的回归）：把自动触发改成"仅 UIA"后，终端 / Electron / 部分 Qt 程序读不到选中文本，
浮动条**完全不出现**。

**最终方案**（`capture.go` `captureForGesture`）：
```
UIA 优先
  ↓ 读不到
模拟 Ctrl+C 兜底
  ↓ 但跳过：设置=仅 UIA / 前台是 explorer.exe 或 desktop.exe
```
设置页「取词方式」提供三档：自动 / 模拟复制 / 仅 UIA。

**顺带修的严重性能 bug**：`processNameOf`（OpenProcess + QueryFullProcessImageName）原本在
**鼠标/键盘钩子回调里同步执行**。低层钩子跑在输入线程上，整个桌面都在等它 —— 这是"快"词典反而让
全系统输入变卡的原因。已移入 goroutine。

## 三、设置界面不能滚动 / 不自适应

**根因**：`settingsView` 根 `Row` 只写 `FillWidth()`，没写 `FillHeight()`。Row 高度=内容高度，
内部 `Scroll` 拿到无边界高度，`MaxY` 恒为 0，长页面被裁掉且无法滚动。

**修复**：
- 根 Row 补 `FillHeight()`，Scroll 补 `FillHeight()` + `ScrollbarInsets`
- 接入 `ui.ScrollState` + `TrackScroll`：改设置不跳回顶部，切页面才归零
- 硬编码 `Width(320/300/420)` 的控件全部改为 `Grow(1)` / `FillWidth` / `MaxWidth`

**回归测试** `settings_layout_test.go`：反向验证过 —— 撤掉 `FillHeight` 后测试报
`MaxY=0 ... clipped with no way to scroll`。

## 四、发音机器人音 → 接入 Edge TTS

- `tts.go`（新增）：HMAC-SHA256 签名换 token → POST SSML → mp3，直接喂现有 mciSendString 播放器，零新依赖
- `audio.go`：优先级改为 单词→有道真人音 / 其余→Edge TTS / 最后兜底 SAPI
- 修掉 SAPI 子进程句柄被丢弃、`stopAudio()` 停不掉的问题（句柄已保存，会 kill）

音色：en-US-AriaNeural / en-GB-SoniaNeural / zh-CN-XiaoxiaoNeural / 日韩法德西俄各一。

# 追加修复（同日第二轮）：悬浮条完全不出来

用户反馈“划词根本没有悬浮条”。实测定位到**三个叠加的 bug**，全部与钩子有关，
而且是同一个症状：钩子“装上了、返回成功、但回调永远不被调用”。

## Bug 1：CallNextHookEx 的 hhk 传了 0

微软文档说这个参数“会被忽略”，但传 0 会让系统把钩子从链上摘掉。
症状：SetWindowsHookEx 返回有效句柄，回调只被调用一次（或零次），之后再无事件。

**验证方法**：写一个 30 行独立探针，对比 hhk=0 和 hhk=真句柄：前者 count=0，后者 count=1152。

**修复**：保存 liveMouseHook / liveKeyHook，回调里回传各自句柄。

## Bug 2：钩子装在不会 pump 消息的线程上

WH_MOUSE_LL 的回调是通过**向安装线程投递消息**来触发的。原来用 mygo.RunOnMain 安装，
而那个线程不跑消息循环 → 钩子装了但永不触发。

**修复**：专用线程 hookLoop()，runtime.LockOSThread() 锁定，自己跑 GetMessage/TranslateMessage/DispatchMessage。

## Bug 3：拖拽归属窗口取错

hookTarget = foregroundWindow() 在按下瞬间取前台窗口。当有置顶的 fastDictionary 窗口
（设置页、钉住的弹窗）时，前台永远是它自己 → isOwnProcess 判定为“自己的窗口” → 丢弃每一次划词。

实测日志：rejected="fast词典 设置"/"MyGoWindow"。

**修复**：拖拽结束时用 WindowFromPoint 按**鼠标位置**取窗口，而不是用按下时的前台窗口。

## 诊断工具（保留）

--hookstats 每秒打印钩子统计：

    hook events=42 down=1 up=1 drag=1 skippedOwn=0 rejected=""/""

- down/up = 左键按下/抬起次数
- drag = 判定为划词拖拽的次数
- skippedOwn = 因为“是自己的窗口”被丢掉（这个 >0 就是 Bug 3）
- rejected = 被丢掉的窗口标题/类名

## 回归测试

hook_test.go 三条：TestCallNextHookExUsesTheLiveHandle、TestHooksRunOnAPumpingThread、
TestGestureOwnerComesFromThePointer。这些是结构性断言（读源码），
因为在无头环境里无法真的装钩子收事件。

## 踩坑记录

- 测试时用 SetCursorPos **不会**产生 WM_MOUSEMOVE 给低层钩子，
  必须用 mouse_event(MOUSEEVENTF_MOVE, dx, 0, ...) 做相对移动，否则 drag 永远是 0。
- 不要往钩子回调里写 log.Printf：低层钩子有 LowLevelHooksTimeout（默认 300ms），
  超时会被系统静默卸载。诊断计数用 atomic，日志在普通 goroutine 里打。

# 追加修复（第三轮）：段话发音慢 —— 已撤销的错误方案

用户反馈：一段话发音要十几秒。

## 错误方案（已撤销）

我第一版做的是「按句切块 + 流水线播放」。**这是错的**：每块单独合成，
会给每句重新套一次句末语调和重音，整段听起来断断续续、重音错位。
`speech_chunks.go` 及其测试已删除。

## 真正的原因

不是合成本身慢。实测（整段一次请求）：

| 文本 | 合成 | 开始播放 | 到出声总计 |
|---|---|---|---|
| 单词 | 558ms | 74ms | 632ms |
| 一句话 | 466ms | 33ms | 499ms |
| 250 字符 | 531ms | ~0ms | 531ms |
| 600 字符 | 621ms | 10ms | 632ms |
| 322 字符（含 token 冷启动） | 854ms | 99ms | 952ms |

整段一次合成本来就在 1 秒内出声，**切句没有任何收益，只有副作用**。

「十几秒」的真实来源是两点，都已修掉：

1. **Token 握手落在热路径**：每次的首句要额外付 ~650ms 的签名换 token。
   已改为启动时 `warmEdgeTTSAuth()` 后台预热。
2. **MCI 播放完成判定错误**（这个是真正的元凶）：`status mode` 在 `play`
   后的头几毫秒返回 `MCIERR_UNSUPPORTED_FUNCTION (263)`，被误判成"已停止"。
   现在改成先用 `playMP3` 异步播放（不等完成），只有需要顺序时才用
   `playMP3Blocking` 轮询 position/length。

## 当前实现

`PlaySpeech` → 单词走有道真人音 → 其余走 Edge TTS **整段一次请求** → `playMP3` 异步播放。
不做任何切分，语调和重音完全交给神经语音模型。
