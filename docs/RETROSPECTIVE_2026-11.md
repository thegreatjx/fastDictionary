### 2.3 验证本身也在返工

在 1.4.5 的验证过程中实际发生过：

- 截到旧预览进程的界面，构建因 exe 被占用而失败；
- 用 `--page home --shot-window settings` 截到的是通用页，因为 `home` 被重定向；
- 配置是 sky，截图却是 mint，因为预览 exe 名不同、读的是另一份用户数据；
- 单实例锁把新进程的参数交给旧进程，看起来“新版本没生效”；
- 长难句窗口是隐藏的，普通截图拿不到，必须走 `mygo-automation`。

每一次都不是代码错，而是**验证证据没有身份**：不知道图来自哪个 commit、哪个 exe、哪份配置、哪个主题。于是“看过了”不能证明“这版对”。

### 2.4 发布节奏由反馈驱动

24 个包中，16 个仍叫 `1.1.0`。版本号、包名、源码提交、运行进程、截图之间没有一份共同的清单。结果是：

- 用户无法从版本号判断行为差异；
- 每个微修复都重新走一遍完整出包与手工检查；
- 同一个类别的下一个症状出现时，上一轮的检查记录无法复用。

## 3. 根因：边界处的两份真相

### 3.1 第一性原理

功能内部的逻辑通常有测试，真正容易错的是**两个表示形式的接缝**：

```
设计意图  ↔  像素
模型输出  ↔  解析器  ↔  持久化配置
构建产物  ↔  包  ↔  运行进程  ↔  截图
用户动作  ↔  请求  ↔  结果状态  ↔  UI
```

接缝两侧只要各有一份可以独立演化的“真相”，且没有可执行的不变量，漂移就只是时间问题。缺陷出现在用户面前时，看起来像“功能坏了”；开发者按可见症状修其中一份真相，测试只覆盖被修的那份，下一次就从另一条路径复发。

**这不是“测试不够多”，而是测试和证据只证明了其中一份真相。**

### 3.2 五组双源

| 边界 | 真相 A | 真相 B | 典型事故 |
| --- | --- | --- | --- |
| 设计 | `DESIGN.md` 的角色描述 | `theme.go` + 组件里的字面量/借用色 | 难点用 Warning 琥珀、从句铺 30% 徽章色、写作高饱和红 |
| 模型协议 | 提示词要求 | 解析器接受 + 配置里持久化的旧提示词 | 旧 `annotations` 指令配新 `segments` 解析器，整卡静默回退 |
| 模型输入 | 模型声称的分段 | 原文 | 错序/改写/伪造主句时，要么整卡放弃，要么把模型词显示出来 |
| 构建 | 源码 commit | exe / 包 / 运行进程 / 截图 | 截到旧进程、旧配置、另一套主题 |
| 结果 | “请求已发/函数返回” | 后置条件是否成立 | 保存未落盘却显示 ✓、过期精译覆盖新输入、复制后不重绘 |

### 3.3 两个放大器

1. **代理指标替代真实观测。** 用“方向变了”判断窗口是否震荡，而不是“窗口尺寸是否真的变了”；用“函数没报错”判断保存成功，而不是“文件已写入且可读回”；用“界面上有卡片”判断解析成功，而不是“结构化分段覆盖了原文”。
2. **失败伪装成成功。** 长难句解析失败时仍显示“原句 + 译文”，保存失败只写日志，复制成功但界面不重绘。用户看到的是一个“看起来正常”的界面，于是问题被推迟到下一次使用才暴露。

### 3.4 为什么已有资产没挡住

- `docs/STATE_MACHINES_FIX_PLAYBOOK.md` 已经系统处理了请求令牌、generation、recover 契约，但它管的是**数据流状态机**；本次重复主要集中在视觉、协议与验证身份。
- `docs/DESIGN.md` 是散文契约，能被人读懂，但不能被 CI 执行。组件仍然可以写 `at.Warning` 或 `ui.Hex` 而不被拦住。
- 测试覆盖了“新格式 + 正常输入”，没有覆盖“旧配置 + 真实模型的错序输出”。
- `CHANGELOG.md` 记录的是事后结果，不是事前门槛；它无法阻止第 24 个包。

## 4. 修复：把真相收口成可执行契约

本次不追求“再修一个症状”，而是给每个边界加三样东西：**唯一真相、可执行不变量、带身份的证据**。

| 契约 | 唯一真相 | 可执行检查 | 落地 |
| --- | --- | --- | --- |
| C1 设计角色 | 所有颜色只在 `theme.go`；组件只消费语义角色 | 全强调色 × 明暗对比度测试；难度色不得等于 Warning/Danger | `theme_contract_test.go`、`grammarDifficultyPalette`、`grammarClauseColors` |
| C2 模型协议 | 提示词版本与解析器版本成对升级；持久化配置有迁移 | 迁移测试；错序/伪造主句/半截从句/整段改写 fixture | `grammar_protocol_test.go`、`ensureDefaultActions` |
| C3 验证证据 | 一份 manifest 绑定 commit / exe SHA / 配置 / 主题 / 强调色 / 时间 | `scripts/ui-evidence.ps1` 拒绝无身份截图；隔离用户数据 | 新增脚本与 Skill |
| C4 结果后置条件 | 成功 = 后置条件成立，不是“调用返回” | 复用 `requestToken`/generation；新路径必须带请求身份 | 既有状态机契约 + 交付规则 |
| C5 优先级 | 每个多来源决策有一张显式优先级表 | 双来源、回声、中英混排 fixture | 既有测试 + 交付规则 |
| C6 发布批次 | 一个已验证的类别一个包，不按微修复出包 | 发布前跑证据 harness 与全量检查；同一天不重复出同版 | `AGENTS.md`、`docs/ENGINEERING_CONTRACT.md` |

### 4.1 设计：颜色从“值”变成“角色”

- `grammarClausePalette` 从 `grammar.go` 移到 `theme.go`，返回值从三个位置参数改成具名结构 `grammarClauseColors{wash, badgeBg, badgeText}`。1.4.5 的根因之一就是调用点取错了第二个返回值，把 30% 徽章色铺到整段从句上；具名字段让这个错误无法再写出来。
- 新增 `grammarDifficultyPalette`。难点是信息，不是警告；颜色角色固定为中性卡面 + 主题色圆点，测试禁止它等于 `Warning`/`Danger`。
- 测试用真实的 `applyTheme` 构造 4 套强调色 × 明暗两套主题，检查标题、开关、六类从句徽章、难点文字、写作删除/新增的对比度。首轮就发现 sky 浅色徽章 4.35:1、dark 徽章 4.47:1、mint dark 4.21:1，均已修正。
- 难点说明文字从 `TextMuted` 改为 `TextSec`：11px 的说明不是角标，暗色下 `TextMuted` 只有约 3:1。
- 从句徽章加 `NoWrap()`，避免两个汉字在行尾被拆成“宾 / 从”。

### 4.2 协议：宽容输入，严格输出

`ParseSentenceAnalysisDetailed` 的契约被固定为：

- **输入宽容**：接受错序、标点变体、只标半截从句、把主句误列为从句；
- **输出严格**：所有显示文字必须切自原文；无法对齐就显式回退，不显示模型改写的词；
- **失败可见**：`ParseOutcome` 区分 `structured`/`translation_only`/`fallback_direct`/`failed`，卡片说明为什么没有结构。

新增 fixture 覆盖 1.4.4 的真实形态：模型把 `before the meeting` 排在主句前、把主句列为 `c0`、只给从句前半段 `clause_id`。解析结果仍为 `structured`，分段拼接与原文完全一致，`c0` 被丢弃，后半段延续 `c1`。

配置迁移补上了 V3 → V4 的 `OutputSchema`：只迁移提示词、不迁移 schema，会让设置页继续显示 `segments/clauses/translation`，而 V4 还会输出 `difficulties`。迁移只在提示词确实被升级时发生，用户自己配的 V4 提示词 + 自定义 schema 不动。

### 4.3 验证：每张图都要有身份证

新增 `scripts/ui-evidence.ps1`：

- 用 `-tags e2e` 构建独立 exe `fastDictionary-uiverify.exe`，数据目录因此是 `%APPDATA%\fastDictionary-uiverify`，不碰真实配置；
- 每次重建 fixture `config.json`，显式写入 `theme_mode`、`accent_theme`、`onboarded` 与不冲突的快捷键；
- 启动后连接 `MYGO_AUTOMATION`，自动选择非隐藏窗口，抓取原生 `screenshot` 与 `snapshot -i --full`；
- 写 `manifest.json`：commit、工作区是否干净、exe SHA256、配置路径与内容、主题/强调色、窗口、时间、Go 版本；
- 只停止自己启动的 PID，结束后删除 fixture 与 socket（`-Keep` 可保留）。

视觉结论必须同时给出 `manifest.json`、截图和控件树。没有 manifest 的截图不算证据；`ui.Tester` 的 headless 渲染不能替代真实窗口。

### 4.4 发布：批量验证，减少包

`AGENTS.md` 增加发布批次规则：

- 同一类问题在一次修复中收口，验证通过后只出一个包；
- 出包前必须跑 `ui-evidence`（涉及界面）或对应 fixture（涉及协议/优先级）；
- 只改测试、文档、脚本且不改变二进制行为的提交，不重新出包；
- `CHANGELOG` 的发布记录必须包含源码提交、包名、SHA256、测试数与证据路径。

## 6. 下一次怎么判断没有重犯

1. 新界面元素是否能说出它的**角色名**？如果只能说出颜色值，契约还没建立。
2. 改动模型协议时，提示词、解析器、持久化配置是否**同一次提交**升级？旧配置是否有 fixture？
3. 视觉结论是否附 `manifest.json`？manifest 里的 commit/exe/theme 是否与当前工作区一致？
4. 成功路径是否有**后置条件**？失败时界面是否明确说明，而不是显示一张“看起来正常”的卡？
5. 这个包是否代表一个**已验证的类别**，而不是一个刚修好的症状？

观察指标：每周分发包数、返工提交占比、无 manifest 的视觉结论数、同一类别重复修复次数。目标不是零 bug，而是**同一类 bug 不支付第二次**。
