## 2. 你的网络环境实测（2026-10-10，第二轮修正）

> 第一轮结论有误（按 pot 的旧实现测微软所以 404）。你指出阅读蛙插件谷歌/微软都免费可用——查证 read-frog 源码（mengxi-ream/read-frog，已 clone 到本地）后确认：**微软 2026-07 移除的只是 token 端点，替换成了免鉴权新端点**。第二轮实测：

| 接口 | 状态 | 延迟 |
|---|---|---|
| **微软 translatetext（新，免鉴权）** | ✅ **3/3 成功，自带语言检测**（detectedLanguage） | **195–560ms，稳定** |
| 谷歌 gtx（translate.googleapis.com） | ✅ 200（比 translate.google.com 稳） | 677ms–1.8s，**间歇 429** |
| 百度 langdetect（无 key） | ✅ 200 | 113–440ms（快通道已不需要：微软响应自带检测） |
| 有道 suggest（词典） | ✅ 200 带释义 | ~150ms |
| 百度 ait / 腾讯 transmart / 有道 web / 搜狗 / DeepL | ❌ 需签名/token/key | - |

**微软新端点要点**（read-frog microsoft.ts 注释 + 本机实测验证）：
- POST https://edge.microsoft.com/translate/translatetext?from=&to=zh-Hans&isEnterpriseClient=false
- body 是**裸 JSON 字符串数组** ["text1","text2"]（旧 [{Text}] 形状会被拒）；from="" 即自动检测
- 不支持 HTML 片段；响应含 detectedLanguage——连语言检测那一次网络调用都省了

**快通道最终策略（已实现进 fastpot）**：
1. **微软 + 谷歌双路竞速**：并发发出，先回先用，输家立即 cancel——谷歌的间歇 429 被微软完全掩盖（实测 6 轮全部微软胜出，195ms–1s）
2. 语言方向用**本地启发式**（unicode 范围判 CJK/假名/谚文/拉丁，零网络开销），引擎返回的真实检测结果仅作展示
3. **单词模式**：isWord 命中时追加一次 gtx dt=bd 词典请求（词性分组+音标）；谷歌 429 时词典缺失但不影响译文
4. 可选加固（未做）：百度开放平台免费 appid 作第三路；有道 suggest 补词典

## 3. 框架选型结论（你已拍板 mygo）

**mygo（egoist/mygo）v0.3.7**，2026-09-26 首发（仓库创建日），1269 star，作者 egoist（知名开源作者，ouo/press 等）。

为什么适合「唤醒快」：
- **原生 UI 模式**：窗口内容是 Go 画的 GPU 场景（D3D11），**无 WebView、无 HTML/JS 加载**——官方定位就是 "the window opens at once and takes little memory"。pot 的冷建窗+React bundle 加载被整体消灭
- 纯 Go 无 cgo，单二进制（fastpot 实测 18.2MB，常驻内存实测 **23.4MB**，pot 冷启动 61MB+）
- 全局快捷键/托盘/剪贴板/多显示器 DPI API 齐全（native.md 已核实）
- Typed IPC + channel 流式 → 以后接 AI 长文精翻（SSE 流式回 UI）正好用
- **同一 app 可混两种窗口**：划词弹窗=原生 UI（快），设置/长文阅读=WebView+React（富交互）

风险与对策：
- 项目仅 2 周历史（v0.1.0→v0.3.7 迭代很快，42 open issues）→ **锁定 v0.3.7，不追新**；API 以 Go module 缓存源码为准（本次已实践）
- Go 1.27+ 要求 → 你机器 go1.27.0，mygo 自动下载 1.27.2 toolchain，已验证可用
- 无现成 OCR/截图生态 → 后续用 Windows.Media.Ocr（purego 调用）或挂 tesseract sidecar

对比（为什么不选其他）：
- **Tauri 2**：稳定但弹窗仍是 WebView2 冷启动，与「唤醒快」的核心诉求冲突；Rust 生态好但你要的是快
- **Wails v3**：beta.28，纯 WebView 路线，同样没有原生弹窗能力
- **Electron**：内存/启动都更重，直接排除

## 4. 产品分层（你的核心诉求 → 架构）

```
┌─ 快通道（目标 <600ms，无 key，热路径零 WebView）─────────┐
│ 划词弹窗：全局热键 → 原生UI窗(常驻隐藏，Show即达)         │
│ 引擎：微软 translatetext ⇄ 谷歌 gtx 双路竞速，先回先用    │
│ 方向：本地 unicode 启发式（零网络）；引擎检测仅作展示      │
│ 词典：单词 → gtx dt=bd 词性分组+音标（429 时优雅降级）    │
│ 历史：SQLite（沿用 pot history.db 思路）                  │
└───────────────────────────────────────────────────────┘
┌─ 精读通道（AI = magpie 网关，已实测打通）─────────────────┐
│ http://127.0.0.1:3425 · magpie v0.1.1158 · 29 个模型      │
│ 划词窗加「AI 精翻」按钮：当前文本 → magpie 流式重译        │
│   模型 group/auto-deepseek-v4-1-flash + reasoning low     │
│   （实测：翻译请求 reasoning_tokens=0，快且免思考）        │
│ 推理档位映射：低=flash/low · 中=flash/high · 高=大模型     │
│ 长文/文件(docx/pdf/epub) → 分段流水线 → SSE 流式渲染      │
│   （mygo typed IPC + channel 正好承载流式；WebView 窗）    │
│ UI：React + web-design-guidelines/frontend-design skill   │
└───────────────────────────────────────────────────────┘
```

关键性能设计（对照 pot 病灶逐条修）：
1. **翻译窗常驻隐藏**（Hidden:true 建一次，热键只 Show+SetPosition）——pot 是每次 build_window，本 demo 已按常驻实现
2. 弹窗 Show 与取词、翻译请求**并行**发出，UI 先渲染源文+spinner，网络回来再 Update
3. 原生 UI 无 bundle 加载；状态用 mutex+snapshot，win.Update 触发重绘（已实现）
4. OnBlur 即 Hide（pot 的 100ms blur 竞态逻辑简化掉）
5. 语言方向本地判定（unicode 启发式），不再为 detect 多打一次网络——微软响应自带 detectedLanguage
